# Secrets policy

This repo will eventually be made public. **No secret material is ever
committed.** Read this before adding anything that looks like a credential.

## What counts as a secret

- Private keys (any `*.pem`, `*.key`, `*.p12`, `*.jks`, `*.pfx`)
- API tokens, app secrets, OAuth client secrets, signing secrets
- Salesforce session tokens, refresh tokens, JWT bearer assertions
- AWS access keys, Heroku auth tokens, Slack bot tokens, Tableau tokens
- Anything in `.env`, `secrets/`, `.secrets/`, `.heroku/`

## How secrets are handled in this project

| Layer | Where they live | How they get there |
|-------|-----------------|---------------------|
| **Local dev** | `secrets/` and `.env` (both gitignored) | Generated by scripts in `scripts/`, or copied from a 1Password vault, or pasted from another team member out-of-band |
| **Heroku runtime** | Heroku Config Vars | `heroku config:set KEY="$(cat secrets/the-file)"` — never via the dashboard with copy-paste, never via a committed file |
| **GitHub Actions (future)** | GitHub Actions Secrets / Environments | Set via repo Settings → Secrets and variables. Read by workflow YAML as `${{ secrets.X }}` |

## Guardrails enabled on this repo

- `.gitignore` blocks `*.pem`, `*.key`, `secrets/`, `.env`, etc. (see `.gitignore`)
- **GitHub Push Protection** on the `t-birke/skywave-interactive` repo — must be enabled in Settings → Code security. Blocks pushes that contain known secret patterns (AWS keys, Salesforce tokens, etc.). Free.

## What to do if a secret is accidentally committed

1. **Rotate it immediately.** Assume it is compromised. Do not waste time
   trying to remove it from history first.
2. After rotation, scrub git history with `git-filter-repo` and force-push
   (only if the repo isn't public yet). If it's already public, history
   rewriting doesn't help — only rotation does.
3. Document the incident in `SECRETS.md` so future-you knows it happened.

## Credential inventory (where each secret lives)

Check here FIRST before regenerating or re-deriving any credential.

| Secret | Store | Notes |
|--------|-------|-------|
| Heroku Relay app consumer key | `.env` → `SF_CLIENT_ID` | JWT app for the consumer site (`Skywave_Heroku_Relay`). Private key: `secrets/jwt.key`. |
| Data Cloud app cert + key | `.secrets/dc.crt`, `.secrets/dc.key` | For `Skywave_DataCloud_Integration`. `dc.key` matches the cert deployed in the Connected App. For direct Data Cloud API calls (sf-datacloud-api-auth skill). |
| Data Cloud ingest cert + key | `.secrets/dc_ingest.crt`, `.secrets/dc_ingest.key` | Second keypair for the ingest scope. |
| **data360 MCP credentials** | **`.secrets/dc.env`** | Canonical store for the data360 MCP server's auth. The MCP jar supports ONLY static `access_token` or `client_credentials` — **NO JWT/private-key input**. Use client_credentials: consumer key + secret of `Skywave_DataCloud_Integration`. Consumer secret is fetch-once from App Manager → Manage Consumer Details. |
| **ipinfo.io token** | **Heroku Config Var `IPINFO_TOKEN`** on `skywave-app` | Client-side IP geolocation token (free tier). Served to the browser via `/api/config` → `site.js loadGeo()`; the consumer site calls `https://ipinfo.io/json?token=…` to resolve the visitor's city + lat/lon, which derive `Contact.Home_Airport__c`. The token IS exposed to the browser by design (ipinfo scopes it), so it's low-sensitivity, but it's still kept out of git per this policy. To view/rotate: ipinfo.io dashboard → Token; then `heroku config:set IPINFO_TOKEN="…" -a skywave-app`. Rotated 2026-06-05. If unset, geolocation silently no-ops (no home-airport pre-fill). |
| **Website proof-cookie HMAC key** | **Heroku Config Var `SKYWAVE_PROOF_KEY`** on `skywave-app` | HMAC-SHA256 secret that signs the `skywave_proof` httpOnly cookie sealing the visitor's WebSDK deviceId. Without it the relay refuses to start. Generate via `openssl rand -base64 48`; rotation invalidates all in-flight cookies (visitors transparently re-init on next request). Never expose to the browser. To rotate: `heroku config:set SKYWAVE_PROOF_KEY="$(openssl rand -base64 48)" -a skywave-app`. |
| **Website JWT identity** | `.env` → `SF_USERNAME=skywave.website@skywave-interactive.demo`; same `SF_CLIENT_ID` as the relay app | Pre-authorized on the `Skywave_Heroku_Relay` Connected App via the `Skywave_Heroku_Website` permset (UI: Setup → App Manager → Manage Permission Sets). Has Contact CRUD via that permset; the integration user that drives the phone-demo path stays minimal. Switching JWT subjects is a `heroku config:set SF_USERNAME=…` and a redeploy — no code change. |
| **MIAW User Verification keypair** | `.secrets/miaw_identity_{private,public}.pem` + `.secrets/miaw_identity_cert.pem` + `.secrets/miaw_identity_jwk.json`; Heroku Config Vars `SF_MIAW_JWT_PRIVATE_KEY` (PEM), `SF_MIAW_JWT_KID`, `SF_MIAW_JWT_ISSUER` | Dedicated RSA-2048 (RS256) keypair, SEPARATE from the SF JWT-bearer key. Signs the `customerIdentityToken` (sub=deviceId) that `src/miaw-identity.js` mints and the custom chat client passes to the *authenticated* MIAW access-token endpoint, so the agent resolves the same deviceId-keyed Contact via MIAW User Verification (`MessagingEndUser.MessagingPlatformKey` uid:<deviceId>). The PUBLIC key (`miaw_identity_jwk.json`, kid `4180b5a671fc09eb`) is uploaded to the Salesforce Keyset (Setup → Messaging for In-App and Web User Verification); private key never leaves `.secrets/`/Heroku. Issuer must match the Keyset issuer (`skywave-heroku`). Local dev: `SF_MIAW_JWT_PRIVATE_KEY_FILE=.secrets/miaw_identity_private.pem`. If unset, the client falls back to the unauthenticated token (anonymous chat). Regenerate: `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048`. |

## Files that look secret-ish but are NOT

- `force-app/main/default/connectedApps/*.connectedApp-meta.xml` —
  contains the consumer key and a public cert; both are fine to commit.
- The `.agent` files in `aiAuthoringBundles/` — agent definitions, no
  credentials.

## Required env vars per component

See `.env.example` at repo root for the canonical list. Copy it to `.env`
and fill in real values for local dev.

## Generating things

- JWT keypair for the Salesforce Connected App: `scripts/gen-jwt-keypair.sh`
  (writes `secrets/jwt.key` private key + `secrets/jwt.crt` public cert).
  The public cert gets committed inside the Connected App metadata; the
  private key never leaves `secrets/` or Heroku Config Vars.
